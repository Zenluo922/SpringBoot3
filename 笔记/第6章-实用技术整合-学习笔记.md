## 1.3 PageHelper（讲义：PageHelper整合；MyBatis ch17 的 Boot 版）

**先接旧知识**：MyBatis ch17（10-19）学过 PageHelper——当时要在配置里手动注册 Interceptor 插件。现在 Boot 里一个 starter 依赖搞定，插件自动配好——**这就是 ch4 那句"导入启动器，修改配置文件，就可以完成对应功能的开发"的又一次实例验证**（第三方 starter 的 `.imports` 名单里同样有它，原理完全一致）。

固定三步（顺序不能乱）：

```java
PageHelper.startPage(pageNo, Constant.PAGE_SIZE);  // ① 设置第几页、每页几条
List<Vip> vips = vipService.findAll();             // ② 紧接着查询——PageHelper 拦截 SQL 自动拼 limit
PageInfo<Vip> page = new PageInfo<>(vips);         // ③ 包成 PageInfo：total/pages 都算好了，直接返回
```

⚠️ **最大的坑：startPage 和查询之间不能插别的 SQL。** 原理：startPage 把页码存进 **ThreadLocal**，插件拦截到**下一条**执行的 SQL 时读取并清除它。中间插了别的查询，页码就被那条 SQL 消费掉，真查询反而不分页。口诀：**startPage 紧贴查询**。

PageInfo 常用字段（返回给前端就靠它）：`total` 总记录数、`pages` 总页数、`pageNum/pageSize` 当前页/每页条数、`list` 当前页数据。

依赖：`pagehelper-spring-boot-starter`，Boot 3 配 **2.x** 版本（讲义 2.1.0）。

## 1.4 R 对象（本章第一必会 🔫，黑马点评直接搬）

### 为什么需要它

前后端分离后，后端返回的 JSON 五花八门（有的返回 List、有的返回单个对象、出错时又是另一种结构），前端没法写统一处理逻辑。所以团队约定一个**统一响应格式**，所有接口都套这个壳：

```json
{ "code": 200, "msg": "成功", "data": { } }
```

前端只写一次逻辑：`code == 200` 取 `data`，否则弹 `msg`。

### 设计三要点（面试分水岭，比代码本身重要）

**① 三段式 + 泛型 `<T>`**：code/msg 结构固定，data 类型不定（有时是 Vip、有时是 List<Vip>）→ 泛型化，一个 R 类通吃所有接口。

**② 静态工厂方法 OK()/FAIL()**：不让调用方自己 new + set（容易漏字段、code 随手写错），收口成几个语义明确的工厂方法。配合 Lombok 的 `@Builder` 链式构建（@Builder 需要全参构造器，所以 @AllArgsConstructor + @NoArgsConstructor 是固定搭配）。

**③ 枚举 CodeEnum 收口魔法数字**：第一版的问题——`R.FAIL(400, "修改失败")` 这种字面量散落项目各处，改文案要全局搜索。把 code+msg 对收进枚举常量，调用处变成 `R.FAIL(CodeEnum.MODIFICATION_FAILED)`，改文案只动枚举一个地方。**这是"难以维护 → 可维护"的经典改进，面试讲设计时讲这一步。**

### 讲义改进版 R（照抄可用）

```java
@NoArgsConstructor
@AllArgsConstructor
@Data
@Builder
public class R<T> {

    private int code;   // 业务状态码（不是 HTTP 状态码，见下）
    private String msg; // 提示消息
    private T data;     // 数据体，泛型

    public static <T> R<T> OK() {
        return R.<T>builder()
                .code(CodeEnum.OK.getCode())
                .msg(CodeEnum.OK.getMsg())
                .build();
    }

    public static <T> R<T> OK(T data) {
        return R.<T>builder()
                .code(CodeEnum.OK.getCode())
                .msg(CodeEnum.OK.getMsg())
                .data(data)
                .build();
    }

    public static <T> R<T> FAIL() {
        return R.<T>builder()
                .code(CodeEnum.FAIL.getCode())
                .msg(CodeEnum.FAIL.getMsg())
                .build();
    }

    public static <T> R<T> FAIL(CodeEnum codeEnum) {
        return R.<T>builder()
                .code(codeEnum.getCode())
                .msg(codeEnum.getMsg())
                .build();
    }
}
```

可按需补两个重载：`OK(String msg, T data)`（成功带自定义提示）、`FAIL(int code, String msg)`（配合自定义业务异常，见 1.4 最后一节）。命名大小写看团队习惯（黑马点评里常见小写 `ok/fail`），含义一样。

```java
@NoArgsConstructor
@AllArgsConstructor
public enum CodeEnum {

    OK(200, "成功"),
    FAIL(400, "失败"),
    NOT_FOUND(404, "未找到资源"),
    INTERNAL_ERROR(500, "内部服务器错误"),
    MODIFICATION_FAILED(400, "修改失败"),
    DELETION_FAILED(400, "删除失败"),
    CREATION_FAILED(400, "创建失败");

    @Getter @Setter
    private int code;
    @Getter @Setter
    private String msg;
}
```

### ⚠️ 关键概念：HTTP 状态码 ≠ 业务 code

- 这套规范里，**HTTP 状态码几乎永远是 200**，业务成败靠 body 里的 code 区分。
- 为什么：HTTP 状态码表达"传输层"语义（404 = 路径不存在、500 = 服务器炸了）；而"余额不足"这种业务失败，请求传输本身是成功的，语义上就是 200。
- 好处：前端拦截器统一处理两件事且互不干扰——**网络层错误**（HTTP 非 200，重试/报错）和**业务层错误**（HTTP 200 但 body code 非 200，弹提示）。
- 面试被问"为什么不直接用 HTTP 状态码表达业务失败"就这么答，补一句"统一 200 + 业务码是国内团队主流做法，简单、好统一拦截"。

### 收尾动作：和 ch5 全局异常处理器组装成型 ★

ch5 1.8 你写过 GlobalExceptionHandler，里面用 Map 返回错误。现在换壳：

```java
@RestControllerAdvice   // = @ControllerAdvice + @ResponseBody，错误直接回 JSON
@Slf4j
public class GlobalExceptionHandler {

    // 业务异常：service 层直接 throw，这里接住转 R（BusinessException 记得继承 RuntimeException）
    @ExceptionHandler(BusinessException.class)
    public R<Void> handleBiz(BusinessException e) {
        return R.FAIL(e.getCode(), e.getMessage());   // 用上面补的 (int,String) 重载
    }

    // 兜底：放最后，接没人认领的异常。⚠️ 一定要 log.error！
    // 不然线上只给用户一句"服务器开小差"，自己排查没有任何线索
    @ExceptionHandler(Exception.class)
    public R<Void> handleAll(Exception e) {
        log.error("未捕获异常", e);
        return R.FAIL(CodeEnum.INTERNAL_ERROR);
    }
}
```

**这就是黑马点评"统一响应 + 统一异常处理"改造点的完整形态**，简历上那句"封装统一响应对象 R，配合全局异常处理器统一错误返回"说的就是这两段代码。用法：controller 正常路径 `return R.OK(data)`；出错时 service 直接 `throw new BusinessException(...)`，**不用 try-catch**——异常被 advice 接住转成 R。

## 1.5 事务（本章第二必会 🔫，零配置）

### 为什么零配置

回想两条旧线：
- Spring6 ch16（暂停中）：要用事务得配 DataSourceTransactionManager + 开启 @EnableTransactionManagement；
- ssm-annotation：你手写过事务管理器配置类。

Boot 里这两样都没了——**事务相关的自动配置都做好了**（事务管理器自动注册、事务注解支持自动开启，又是 ch4 那句话）。你只剩一件事：在需要事务的方法/类上标 `@Transactional`。

### 用法（讲义转账例子，两处细节必看）

```java
@Transactional(rollbackFor = Exception.class, propagation = Propagation.REQUIRED)
@Service
public class AccountServiceImpl implements AccountService {

    @Autowired
    private AccountMapper accountMapper;

    @Override
    public void transfer(String fromActNo, String toActNo, double money) {
        Account fromAct = accountMapper.selectByActNo(fromActNo);
        if (fromAct.getBalance() < money) {
            throw new TransferException("余额不足");    // 抛异常 → 本方法内已执行的 SQL 全部回滚
        }
        Account toAct = accountMapper.selectByActNo(toActNo);
        fromAct.setBalance(fromAct.getBalance() - money);
        int count = accountMapper.update(fromAct);
        if (1 == 1) {
            throw new TransferException("转账失败");    // 课程故意抛的，测回滚：上面那条 update 应该没生效
        }
        count += accountMapper.update(toAct);
        if (count != 2) {
            throw new TransferException("转账失败！");
        }
    }
}
```

**细节①：rollbackFor = Exception.class 为什么必写？**

@Transactional 的**默认回滚规则：只回滚 RuntimeException 和 Error**。受检异常（编译器逼你处理的那种，如 IOException）默认**不回滚、照常提交**。业务里受检异常随时可能出现——不写 rollbackFor，转账场景就是钱扣了、到账失败、还提交了。**面试必问，答出"默认只回滚非受检异常"就是分水岭。**

**细节②：propagation = Propagation.REQUIRED 是显式声明默认值**（有事务就加入，没有就新建）。传播行为七种不用背——Spring6 ch16 的债留面试前补，先记住"大多数场景默认 REQUIRED 就对"。

### 位置：类上 vs 方法上

- 标**类上** = 类里所有 public 方法都有事务（省事但粒度粗，查询也开事务）
- 标**方法上** = 精确控制（推荐）
- 纯查询方法可标 `@Transactional(readOnly = true)`，小优化，知道即可

### ⚠️ 事务失效三大场景（面试重灾区，先记结论）

1. **同类自调用**：同一个类里 `this.methodB()` 去调带 @Transactional 的 methodB——调用没经过代理，注解失效。解法：拆到另一个 bean，或注入自己的代理。
2. **方法不是 public**：Spring 事务基于代理增强，非 public 方法增强不到，失效。
3. **异常被 try-catch 吃掉**：方法里 catch 了异常既没抛也没手动 setRollbackOnly，事务管理器看不到异常 → 不回滚。

（冷门第四条：类压根没被 Spring 管理，@Transactional 自然无效。）

**底层一句话串起来：@Transactional 生效靠 AOP 代理——调用必须经过代理对象，代理才能在方法前后做开事务/提交/回滚。三条失效场景全是"绕过了代理"。** 这句说出来，面试官就知道你不是背的。

## 1.6 打 war 包（讲义：SpringBoot打war包；只读，你部署走 jar）

**什么时候才需要 war**：部署到**外置 Tomcat**——公司老项目运维规定、服务器上已有统一管理的 Tomcat。你的项目（学生服务器 + Docker）用 `java -jar` 跑内嵌 Tomcat，**这节不敲，知道步骤**：

1. `<packaging>war</packaging>`
2. starter-web 里**排除内嵌 tomcat**（exclusions 排掉 spring-boot-starter-tomcat）——外面有 Tomcat，不重复打进去
3. 单独再引入 spring-boot-starter-tomcat，**scope=provided**——编译期要用它的 servlet api，但**打包时不进 war**（外置 Tomcat 的 lib 自带）
4. 主类**继承 SpringBootServletInitializer** 并重写 `configure()`——外置 Tomcat 启动时靠它找到你的 Boot 应用（角色相当于传统 web.xml）

jar vs war 对比（README 面试题 #8）：

| | jar（Boot 默认/推荐） | war |
|---|---|---|
| 容器 | 内嵌 Tomcat，`java -jar` 直接跑 | 依赖外置 Tomcat，丢 webapps |
| 部署条件 | 服务器有 JDK 就行 | 服务器要装好配好 Tomcat |
| 产物 | 全部依赖打进一个 fat jar | 部分依赖留在 Tomcat 里 |
| 你的项目 | ✅ Docker 里 `java -jar` | 不用 |

Boot 为什么推荐 jar：内嵌容器让应用**自包含**——"一个文件扔上去就能跑"，不依赖服务器环境，天然适配 Docker/云部署。

# Part 2 骨架速查（懂了之后背这个）

## R 对象三段式（白板默写）

```
R<T> { int code; String msg; T data; }
  ├ R.OK() / R.OK(data)                 成功：200
  └ R.FAIL() / R.FAIL(CodeEnum)         失败：400/404/500…（枚举收口）
原则：静态工厂收口 + 枚举收口魔法数字 + HTTP 恒 200、业务码看 body
```

## 统一响应 + 全局异常成型模板（黑马点评直接抄）

```
controller 正常路径：return R.OK(data);
service 出错：throw new BusinessException(code, msg);   ← 继承 RuntimeException
GlobalExceptionHandler：
  ├ BusinessException → R.FAIL(e.getCode(), e.getMessage())
  └ Exception 兜底   → log.error + R.FAIL(CodeEnum.INTERNAL_ERROR)
```

## 事务要点卡

```
@Transactional(rollbackFor = Exception.class)   ← 必写：默认只回滚 RuntimeException/Error，受检异常照常提交
零配置原因：事务管理器 + 事务注解支持都被自动配置（ch4 那句话又应验）
失效三场景：同类自调用 / 非 public / 异常被 catch —— 根因都是"绕过了 AOP 代理"
```

## PageHelper 要点卡

```
startPage(pageNo, size) → 紧贴查询 → new PageInfo<>(list)
坑：startPage 和查询之间不能插别的 SQL（ThreadLocal 里的页码会被别人消费）
```

## war 三步一句话

packaging=war → starter-web 排除内嵌 tomcat → 主类继承 SpringBootServletInitializer（重写 configure）

# Part 3 高频面试题（本章相关，README 清单 #8 #9 在这里）

### Q1 ⭐⭐⭐⭐ 前后端分离项目，怎么统一响应格式和异常处理？（README #9，结合黑马点评答）

> 封装统一响应对象 R\<T\>：code（业务状态码）+ msg（提示）+ data（泛型数据），所有 controller 返回 R；用静态工厂 OK()/FAIL() 构造，错误码和文案用枚举收口。异常处理用 @RestControllerAdvice + @ExceptionHandler 全局捕获：业务异常转成对应 R.FAIL 返回，再加一个 Exception 兜底防止堆栈泄露给前端（兜底方法里记 error 日志）。我在黑马点评里就是这么做的：接口格式全项目统一，前端只判断一个 code。
> **追问：HTTP 状态码为什么都是 200？** HTTP 码表达的是传输层语义，业务失败时请求传输本身是成功的；统一 200 + body 业务码，前端"网络层错误"和"业务层错误"两套拦截逻辑互不干扰。

### Q2 ⭐⭐⭐⭐ @Transactional 什么情况下会失效？

> 常见三个：①同类内部调用，this 调用绕过了代理对象，事务增强没执行；②方法不是 public，代理增强不到；③异常被 try-catch 吞掉，事务管理器感知不到异常，不回滚。根本原因一句话：**Spring 事务基于 AOP 代理实现，凡是绕过代理的调用，注解就失效**。另外类没被 Spring 管理时也无效。

### Q3 ⭐⭐⭐⭐ rollbackFor = Exception.class 是干什么的？不写行不行？

> 指定遇到什么异常回滚。不写时默认规则是**只回滚 RuntimeException 和 Error**，受检异常（IOException、SQLException 这类）会正常提交——在转账场景就是钱扣了、没到账、还入库了。所以业务写操作必写 rollbackFor = Exception.class，保证任何异常都回滚。

### Q4 ⭐⭐⭐ Boot 项目为什么默认打 jar？jar 和 war 怎么选？

> Boot 内嵌 Tomcat，jar 是自包含的可执行包，java -jar 直接跑，不依赖服务器装没装、配没配 Tomcat，天然适配 Docker/云部署。war 是给外置容器用的（老运维规范、已有 Tomcat 集群），要改 packaging、排除内嵌 tomcat（另以 provided 引回 servlet api）、主类继承 SpringBootServletInitializer。新项目一律 jar。

### Q5 ⭐⭐ PageHelper 分页怎么用？原理知道吗？

> 三步：PageHelper.startPage(页码, 条数) → 紧接着执行查询 → 结果包进 PageInfo（total/pages/list 都算好了）直接返回。原理：startPage 把分页参数放进 ThreadLocal，PageHelper 的插件拦截下层执行的 SQL 自动拼 limit。注意 startPage 必须紧贴查询——中间插了别的 SQL 会把 ThreadLocal 里的页码消费掉，该分页的反而不分页。

### Q6 ⭐⭐ Boot 里事务为什么不用任何配置？

> 相关自动配置都做好了：数据源确定后，事务自动配置自动注册 DataSourceTransactionManager，并自动开启事务注解支持（相当于自动加了 @EnableTransactionManagement），所以只需标 @Transactional。我在 SSM 整合时手写过这两样，迁到 Boot 删掉照样能用，对比非常直观——这就是"手写原型找得到，自动配置就秒懂"。
