# Part 1 人话版：先搞懂（不看懂这部分，后面的总结全是天书）

## 1.1 一句话卸掉神秘感

回想你的 `ssm-annotation` 项目：`DataSourceConfig`、`MybatisConfig`、`WebAppInitializer`……这些配置类是**你自己一个字一个字写的**，没有任何魔法，就是普通的 @Configuration + @Bean。

现在思考一个问题：**Spring Boot 里你一行这种代码都没写，为什么 DataSource、DispatcherServlet 照样存在于容器里？**

答案朴素到可笑：

> **Spring Boot 的作者把"你本来要写的那些配置类"提前写好了，打包进一个 jar，然后想办法在启动时把它们加载起来。**

自动配置 ≠ 黑科技。**自动配置 = 别人替你写好的配置类。**

所以本章的全部内容，其实只是在回答三个朴素的问题：

| 问题 | 答案预告 |
|---|---|
| ① 这些"替你写好的配置类"放在哪？ | 一个叫 spring-boot-autoconfigure 的 jar 里 |
| ② 你的包扫描明明扫不到它，怎么被加载进容器的？ | 不走包扫描，走 @Import 点名导入 |
| ③ 152 个配置类为什么没有全部生效？ | 条件注解筛选，满足条件才生效 |

讲义里每一节，都在回答这三个问题之一。对照表：

| 讲义小节 | 在回答 |
|---|---|
| 两大核心 / 体会便捷 / bean 数量 59→160 | 背景：它到底帮我们干了什么（问题①的动机） |
| 自动配置是按需加载的 / 152 个在哪 | 问题① |
| @ComponentScan / 默认包扫描规则 | 问题②的铺垫：先告诉你扫描扫不到 |
| @EnableAutoConfiguration / ImportSelector 源码跟踪 | 问题② |
| 条件注解 / 26 个生效 | 问题③ |
| 自动配置类干了啥 / 属性类 | 生效**之后**的东西怎么读你的 yml |

## 1.2 问题①：这些配置类放在哪？

顺藤摸瓜看依赖（IDEA 右侧 Maven 面板点开 Dependencies 就能看）：

```
spring-boot-starter-web（你引的，只是张"购物清单"）
  └→ spring-boot-starter（核心启动器，任何 starter 都会连带它）
       └→ spring-boot-autoconfigure ←—— 152 个自动配置类全在这个 jar 里
```

三个 starter 各司其职：
- **starter-web**：声明"我要做 web 开发"，把 web 需要的 jar（spring-webmvc、tomcat……）搬进类路径
- **spring-boot-starter**：核心，每个 starter 都带它
- **spring-boot-autoconfigure**：别人替你写好的那 152 个配置类住这里

**动手验证（2 分钟）**：IDEA 按 Ctrl+N（或双击 shift）搜 `DispatcherServletAutoConfiguration`，打开源码。你会看到：

```java
@AutoConfiguration                          // 本质就是个 @Configuration
@ConditionalOnClass(DispatcherServlet.class) // 类路径有 DispatcherServlet 这个类才生效
public class DispatcherServletAutoConfiguration {

    @Bean
    public DispatcherServlet dispatcherServlet() { ... }   // 注册前端控制器
}
```

看到没有？**@Configuration + @Bean——和你在 WebAppInitializer 里手动注册 DispatcherServlet 是同一件事，只是别人替你写了。** 神秘感去掉一半。

## 1.3 问题②：包扫描扫不到它，怎么加载的？（最难的一步，慢慢来）

先补一个背景知识。Spring 把一个配置类加载进容器，只有两条路：

1. **包扫描** @ComponentScan——"把这一片楼里的人都叫来"：扫主类所在包及子包（你是 `com.powernode.springboot`）
2. **@Import**——"按名单点名"：直接指定类名，指定谁导入谁

再看事实：自动配置类的包是 `org.springframework.boot.autoconfigure`，你的扫描只扫 `com.powernode.springboot`——**根本够不着它**。这就是讲义说的"按说这些自动配置类是无法加载的"。

Boot 的解法：主类上 `@SpringBootApplication` 三合一，其中 `@EnableAutoConfiguration` 的源码里写着：

```java
@Import(AutoConfigurationImportSelector.class)
```

注意这里的套路升级：@Import 不直接点名一个配置类，而是导入一个 **ImportSelector（选择器）**——它的接口方法返回**一批类名**，Spring 把返回的类名全部加载。

比喻升级：包扫描是"把这一片楼里的人都叫来"，@Import 是"按名单点名"，而 **ImportSelector 是"名单本身是动态取来的"**——启动时去仓库（清单文件）里拿一份名单，照着念。

这份"仓库里的名单"长什么样？就是 jar 里的一个文本文件：

```
spring-boot-autoconfigure.jar
  └─ META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

里面一行一个类名，共 152 行。AutoConfigurationImportSelector 启动时读它，把 152 个类名全部交给 Spring。

⚠️ 面试细节：老教程说的 `META-INF/spring.factories` 是 **Boot 2.7 之前**的名单位置，Boot 3 换成了上面这个文件。答出这个是加分项。

到这里：**152 个配置类的类名全部到场。**

## 1.4 问题③：到场 ≠ 生效——条件注解筛选

152 个类名都进了容器，但"到场"和"入职"是两回事。每个自动配置类上都贴着条件（就是你在 1.2 源码里看到的 `@ConditionalOnClass`）：

| 条件注解 | 人话 | 例子 |
|---|---|---|
| @ConditionalOnClass ⭐ | 类路径上**有这个类**才生效 | MailSender 自动配置要求有邮件类——你没导 mail starter，类不存在 → 走人 |
| @ConditionalOnMissingBean ⭐ | 容器里**还没有人干这事**才生效 | 你自己手写了一个 DataSource bean，Boot 的默认配置让位（**用户优先**） |
| @ConditionalOnProperty ⭐ | yml 里有对应**开关/属性**才生效 | 开关型功能 |
| @ConditionalOnBean | 容器里有指定 bean 才生效 | 有 A 才建 B |
| @ConditionalOnWebApplication | 是 web 应用才生效 | |

类比：152 份简历都收到了，HR 按岗位要求筛。你只买了 web 套餐，很多岗位的硬性条件（类路径里根本没有相关类）不满足——**课程实测最后只有 26 个生效**，这 26 个正好是 web 开发的最少配置。

所以"按需加载"的完整含义：**类名全部加载（候选），bean 按条件注册（生效）。** 这两个阶段分开，很多困惑就没了。

**生效 = 自动配置类里的 @Bean 真正注册进容器。哪个类生效，对应技术就整合完成。**

## 1.5 生效之后：yml 里的配置是怎么"传话"进去的

这部分你不陌生——**就是 ch2 你亲手写过的 @ConfigurationProperties**，官方只是把同样的技术用在了自己内部。

链路三步传话：

```
application.yml 写 server.port=8081
   ↓ 绑定
ServerProperties 属性类（头上标着 @ConfigurationProperties(prefix="server")，port 字段被填成 8081）
   ↓ 读取
装配内嵌 Tomcat 的代码从 ServerProperties 里 getPort()
```

所以"改配置文件就生效"没有任何新机制：**组件不直接读 yml，读的是和 yml 绑定的属性类。** 官方文档的 Application Properties 附录，本质就是所有属性类的字段清单+默认值。

一个完整的例子串起来（web 开发最核心的两个）：

| 自动配置类 | 注册的组件 | 配置数据来自 | 你在 yml 里的前缀 |
|---|---|---|---|
| DispatcherServletAutoConfiguration | dispatcherServlet | WebMvcProperties | `spring.mvc.*` |
| 内嵌 Tomcat 自动配置 | tomcat 相关组件 | ServerProperties | `server.*` |

## 1.6 两个 5 分钟实验（建议做，做完这章就"落地"了）

**实验一：亲手体验"导 starter 才有自动配置"**
1. 项目里打印所有 bean 名（讲义代码）：`applicationContext.getBeanDefinitionNames()` 循环打印 → 空项目 59 个
2. pom 加 `spring-boot-starter-web`，刷新，再跑 → 160 个，多了 dispatcherServlet、Jackson 转换器、乱码过滤器……
3. （进阶）再把 starter 注释掉 → 这 101 个 bean 全部消失

**实验二：条件注解小实验**（讲义 AppConfig 例子）
```java
@Configuration
public class AppConfig {
    @Bean public A a() { return new A(); }

    @ConditionalOnBean(A.class)   // 容器里有 A，b() 才执行
    @Bean public B b() { return new B(); }
}
```
把 A 的 @Bean 注释掉，重启，看 B 还在不在。（启动加 `debug=true` 还能看到 CONDITION EVALUATION REPORT：哪些生效、哪些被哪个条件拦下。）

# Part 2 骨架速查：把 Part 1 压成一张图（懂了之后再背这个）

## 完整原理链（白板画这张）

**阶段 A：运行前——依赖准备（把东西搬进类路径）**
```
spring-boot-starter-web → spring-boot-starter → spring-boot-autoconfigure
                                                  （152 个自动配置类 + 名单文件）
```

**阶段 B：运行时——main 之后（筛选、装起来）**
```
main → SpringApplication.run
 └ @SpringBootApplication 三合一
    ├ @SpringBootConfiguration（本质 @Configuration，主类是配置类）
    ├ @ComponentScan（只扫主类根包 → 扫不到 autoconfigure 的包！）
    └ @EnableAutoConfiguration
       └ @Import(AutoConfigurationImportSelector)
          ├ 读 META-INF/spring/...AutoConfiguration.imports → 152 个类名进候选
          ├ 去重 → 剔除 exclude → 条件注解过滤
          └ 26 个生效 → 注册其中一堆 @Bean 组件
             └ 组件 ← 读 ← 属性类(XxxProperties) ← 绑定 ← application.yml
```

## 关键问答（理解深度分水岭）

**Q：包扫描扫不到，152 个类怎么进容器的？**
不走扫描，走 @Import 的 ImportSelector 读名单文件点名导入。**这正是 @EnableAutoConfiguration 存在的意义。**

**Q：152 个都生效吗？**
都进候选，条件注解筛选后按需生效。引 web starter 时实测 26 个。

**Q：为什么"导入启动器，修改配置文件，就能完成功能开发"？**
starter 把类搬进类路径（满足 OnClass 条件）→ 自动配置生效 → 组件从属性类读值（属性类绑 yml）。讲义原话，面试收尾句。

## 数字链（实测，记住增加可信度）

59（空项目 bean）→ 160（引 web starter）= +101 个 web 组件；152 个候选自动配置类 → 26 个生效。

## 对照表：你手写的原型 → Boot 的自动配置（面试差异化素材）

| ssm-annotation 手写 | Boot 自动完成 | 你要做的事 |
|---|---|---|
| DataSourceConfig | DataSource 自动配置 | yml 写 `spring.datasource.*` |
| MybatisConfig（SqlSessionFactory） | MybatisAutoConfiguration | yml 写 `mybatis.mapper-locations` |
| WebAppInitializer（注册 DispatcherServlet） | DispatcherServletAutoConfiguration | 什么都不做 |
| SpringMvcConfig | WebMvcAutoConfiguration | 什么都不做 |
| DataSourceTransactionManager | 事务自动配置 | 直接 @Transactional |

## 条件注解表

⭐ 必认三个：@ConditionalOnClass（类路径有该类）/ @ConditionalOnMissingBean（容器没有该 bean → **用户优先**）/ @ConditionalOnProperty（yml 有该属性）。其余：OnBean / OnMissingClass / OnResource / On(Web|NotWeb)Application。

# Part 3 高频面试题与参考答案

> 标 ⭐ 的必背。答案按"口述 30 秒~1 分钟"的量写，直接背。**前提：Part 1 已看懂，否则背了也经不起追问。**

### Q1 ⭐⭐⭐⭐⭐ Spring Boot 自动配置的原理？

**30 秒版**：
引入 starter → 连带引入 spring-boot-autoconfigure（152 个自动配置类）→ @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector) 加载候选清单 → **条件注解按需筛选**（@ConditionalOnClass 等）→ 生效的自动配置类注册一堆 @Bean → 组件从属性类读值，属性类通过 @ConfigurationProperties 绑定 yml。一句话：**导入启动器，修改配置文件，就能完成对应功能的开发。**

**追问 1：152 个都生效吗？** 不。全部进候选，条件注解筛选后按需生效，引 web starter 实测只有 26 个生效。
**追问 2：候选清单在哪？** Boot 3 在 `META-INF/spring/...AutoConfiguration.imports`；Boot 2 老版本在 spring.factories。
**追问 3：包扫描扫不到 autoconfigure 包，怎么加载的？** 不走 @ComponentScan，走 @Import 的 ImportSelector 读名单点名导入——这就是 @EnableAutoConfiguration 存在的意义。

### Q2 ⭐⭐⭐⭐ 什么是 starter？解决什么问题？

starter 是**一站式依赖集合**：把某功能需要的所有依赖打包成一个，版本由 spring-boot-starter-parent 统一托管（dependencyManagement），所以引依赖不用写版本号、不会版本冲突。它解决"依赖地狱"：以前集 MyBatis 要手动引 4、5 个 jar 并对版本，现在导一个 mybatis-spring-boot-starter 完事。starter 本身不干活，它负责把自动配置需要的类**搬进类路径**，配合自动配置实现"导 starter + 改配置 = 完成功能"。
（注意版本坑：starter 大版本要和 Boot 配套，Boot 3.x 配 mybatis-spring-boot-starter 3.0.x，配成 4.0.1 直接启动冲突。）

### Q3 ⭐⭐⭐⭐ @SpringBootApplication 包含哪些注解？为什么主类要放根包？

三合一：
1. **@SpringBootConfiguration**——本质是 @Configuration，主类本身是配置类；
2. **@EnableAutoConfiguration**——启用自动配置（@Import AutoConfigurationImportSelector）；
3. **@ComponentScan**——组件扫描，默认只扫**主类所在包及子包**。

主类放根包是因为 @ComponentScan 默认扫描范围是主类所在包及子包：放深了，其他包的 @Service/@Mapper 扫不到，注入失败报莫名 NPE。

### Q4 ⭐⭐⭐ 条件注解了解哪些？@ConditionalOnMissingBean 有什么意义？

常见：@ConditionalOnClass（类路径有指定类）、@ConditionalOnMissingBean（容器没有指定 bean）、@ConditionalOnProperty（配置文件有指定属性）、@ConditionalOnBean / @ConditionalOnWebApplication 等。
**意义**：它们是自动配置"按需加载"和"用户优先"的实现——@ConditionalOnClass 让 Boot 只在类路径有对应 jar 时才启用配置；@ConditionalOnMissingBean 让 Boot 的默认配置在用户自己定义了同功能 bean 时自动让位，所以默认配置总能被覆盖而不冲突。

### Q5 ⭐⭐⭐ 在 yml 里改 server.port 为什么就能改端口？

配置修改生效的链路：`server.port` 写进 yml → `ServerProperties` 属性类标了 `@ConfigurationProperties(prefix="server")`，启动时绑定 yml 的值 → 内嵌 Tomcat 的自动配置组件从 ServerProperties 读端口。即**组件不直接读配置文件，读的是和配置文件绑定的属性类**。所有可配置项，官方文档 Application Properties 附录就是全部属性类的清单。

### Q6 ⭐⭐⭐ 内嵌 Tomcat 是怎么回事？

spring-boot-starter-web 连带引入 spring-boot-starter-tomcat（内嵌 Tomcat 的 jar）。启动时 ServletWebServerFactory 相关自动配置检测到类路径有 Tomcat 类，就创建 TomcatServletWebServerFactory 并把 DispatcherServlet 注册进去，随 main 方法启动——不需要外置 Tomcat、不配 web.xml。这也解释了 jar 可以直接 `java -jar` 跑：容器在应用进程里，不依赖外部环境。
（对照：我在 SSM 整合时用 WebAppInitializer 手动注册过 DispatcherServlet 和容器，Boot 的自动配置干的就是同一件事。）

### Q7 ⭐⭐ 怎么让某个自动配置失效？

两种：① 启动类 `@SpringBootApplication(exclude = XxxAutoConfiguration.class)`；② 配置文件 `spring.autoconfigure.exclude=全限定类名`。底层对应 AutoConfigurationImportSelector 里"剔除排除项"那一步。

### Q8 ⭐⭐⭐ Spring、Spring MVC、Spring Boot 三者关系？

Spring 是基座：IoC + AOP 容器，管理 bean 和依赖注入。Spring MVC 是 Spring 生态里的 Web 层框架，基于 Servlet 处理 HTTP 请求（DispatcherServlet 为核心）。Spring Boot 不是新框架，是**自动配置脚手架**：在 Spring 之上通过 starter + 自动配置消除样板配置，内嵌容器让应用独立运行。一句话：**Boot 加速了 Spring（含 MVC）的搭建，三者的运行核心仍是 Spring 容器。**

### Q9 ⭐⭐（加分项）如果让你自定义一个 starter，怎么做？

1. 建两个模块：`xxx-spring-boot-starter`（依赖聚合）+ `xxx-spring-boot-autoconfigure`（写自动配置类）；
2. 自动配置类用 @AutoConfiguration 标注，里面 @Bean 装配核心功能类，用 @ConditionalOnMissingBean 保证用户可覆盖，需要配置就写 @ConfigurationProperties 属性类；
3. 把自动配置类全限定名注册进 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`；
4. 别人引 starter + 改配置文件即可使用——和官方 starter 一模一样的套路。
（答出"注册清单文件 + 条件注解保证可覆盖"两个点就够实习面试了。）

### Q10 ⭐⭐ 如何证明你理解自动配置？（开放题，主动展示差异化）

主动讲实践证据："我手写过 SSM 整合的每个配置类（DataSource、SqlSessionFactory、DispatcherServlet 注册、事务管理器），又在 Boot 里打印过容器 bean 名单做对照——比如 WebAppInitializer 手动注册 DispatcherServlet 这件事，在 Boot 里由 DispatcherServletAutoConfiguration 完成。所以自动配置对我不是黑盒，每个默认组件我都知道它的手写原型。"
